## Источники и границы доказательств

PDF содержит техническое изложение исходной сессии и три фрагмента скриншотов повторной проверки от 22 октября. Исторические результаты ниже приводятся **по тексту отчёта**: отдельные снимки успешных сеансов walter/hank, принятия User Flag, интерфейса контрактов, FTP, cron и restore в приложении отсутствуют.

Скриншоты на странице 7 документируют неудачную повторную регистрацию узла и диагностические HTTP-запросы. Они не доказывают повторное выполнение команд. Доступный текст переписки дополнительно содержит приглашение `hank@blocksynergy` и вывод локального FTP, но не заменяет доказательства всей цепочки.

Адрес экземпляра менялся после перезапусков. Пароли, ключи и значения флагов не публикуются. Исследование относится к одному лабораторному экземпляру HTB.

## 1. VIP и Node Management

В исходной сессии приложение приняло транзакцию кошелька. До операции VIP-страница отвечала HTTP 302, после неё были зафиксированы HTTP 200 и доступ к Node Management.

Материалы не устанавливают точную причину изменения VIP-статуса. По этим наблюдениям нельзя восстановить подтверждённую уязвимость транзакции или утверждать обход проверки кошелька.

## 2. Серверные запросы и внутренний интерфейс

По исходному отчёту, Node Management отправлял HTTP-запрос с сервера на контролируемый исследователем адрес и возвращал данные узла. Отдельная проверка перенаправления показала достижение внутреннего административного интерфейса серверным клиентом: в ответе был его HTML.

Это описывает SSRF и пересечение границы между внешним веб-интерфейсом и внутренним сервисом. В отчёте используется классификация CWE-918. Полного набора исходных запросов, ответов и настроек перенаправления в PDF нет.

## 3. Выполнение команд как walter

Отчёт связывает первоначальный доступ с административной функцией Ping Node. Согласно приведённому анализу, обработчик собирал команду из пользовательского ввода и передавал её оболочке — механизм командной инъекции, обозначенный в отчёте как CWE-78.

Для первой сессии записан результат:

```text
uid=1000(walter)
```

Это исторический результат по тексту источника. Полный воспроизводимый запрос и снимок успешной оболочки в предоставленном PDF отсутствуют.

### Что произошло при повторной проверке

После перезапуска HTTP 200 сопровождался сообщением `No Wallet loaded`. Регистрация узла не подтвердилась:

```text
Registration HTTP: 200
Node registered: False
Node ID not found
```

Два замера составили 0,578921 и 1,063821 секунды. Эти результаты не подтверждают выполнение команды с ожидаемой задержкой. HTTP 200 сам по себе также не подтверждает ни VIP-доступ, ни успешную регистрацию. Иллюстрации приведены на странице 7 PDF.

## 4. Smart Contract Development Server и hank

В исходном отчёте указаны два Python-процесса с разными владельцами:

| Компонент | Контекст |
|---|---|
| Основное веб-приложение | walter |
| Smart Contract Development Server, локальный TCP 5000 | hank |

Сервис разработки принимал контракты в JSON и поддерживал операции с тестовыми контрактами. После работы с импортом и обработкой контракта в первой сессии был зафиксирован успешный SSH-вход как `hank` с аутентификацией по ключу.

Источник связывает переход с обработкой файлового пути в данных контракта. Однако конкретная операция записи и возможность записи произвольного файла не установлены представленными доказательствами. Поэтому публикация не приписывает сервису подтверждённый механизм arbitrary file write и не дополняет цепочку вымышленным payload.

По исходному отчёту, User Flag был получен и принят платформой в этой первой сессии. Отдельного скриншота принятия флага в PDF нет.

## 5. Локальное FTP-хранилище

По отчёту, на TCP 15432 работал локальный vsFTPd 3.0.5; `docker-proxy` перенаправлял порт в контейнер. Аутентифицированный доступ позволял работать с каталогом загрузки и архивом staging.

Доступный текст сессии содержит чтение списка файлов:

```bash
curl --noproxy '*' -sS --connect-timeout 5 --max-time 15 \
  -u ftpuser --list-only ftp://127.0.0.1:15432/upload/
```

Пароль вводится интерактивно и в публикацию не включён. В ответе был указан:

```text
_opt_staging.tar.gz
```

Согласно PDF, в контролируемом тесте FTP принял переименование тестового файла поверх существующего назначения; после проверки тестовые данные удалили. Это наблюдение подтверждает возможность замены в хранилище, но само по себе не доказывает использование изменённого архива привилегированной службой.

## 6. Плановое резервное копирование

Исходный отчёт описывает root-задание cron с периодом пять минут. Мониторинг файловых событий зафиксировал создание и завершение записи временного архива размером **11 380 854 байта**. SHA-256 сохранённой копии совпал с SHA-256 архива в FTP-хранилище; сами значения хешей в PDF не приведены.

По дереву процессов `tar` создавал архив в рамках резервного копирования. Совпадение времени, событий и хешей связывает этот файл с плановым backup.

Создание резервной копии и её восстановление — разные операции. Наблюдение за `tar` в цикле backup не является доказательством извлечения архива службой restore.

## 7. Restore и непроверенная гипотеза TOCTOU

По отчёту, отдельная systemd-служба `restore.service` работала от root. В наблюдаемые моменты её дочерний процесс ожидал; извлечение архива службой в проверенных запусках не зафиксировано.

Исследовалась гипотеза TOCTOU: содержимое ресурса может измениться между проверкой и использованием. Для подтверждения этой цепочки потребовалось бы показать, что служба:

1. Проверила целостность конкретного архива.
2. После проверки получила изменённое содержимое.
3. Извлекла это содержимое с правами root.

Такой последовательности в доступных материалах нет. Проверенная замена файла по FTP не закрывает эти пробелы. Попытки инициировать восстановление не дали подтверждённого извлечения; в тексте сессии тестовый файл `/opt/staging/.bs_restore_test` отсутствовал.

**TOCTOU (CWE-367) остаётся гипотезой. Повышение привилегий до root не завершено.**

## 9. Выводы для защиты

- Ограничивать назначения серверных HTTP-запросов; проверять разрешённость адреса на каждом перенаправлении.
- Запускать диагностические процессы с отдельными аргументами без передачи пользовательского ввода оболочке.
- Ограничивать операции сервиса контрактов рабочим каталогом и минимально необходимыми правами.
- Для восстановления проверять и извлекать один защищённый экземпляр архива, исключая его замену между операциями.
- Раздельно журналировать создание backup, проверку целостности и фактическое извлечение.
